# CAWS Session-Scoped Guard Reprieve — `CAWS-GUARD-REPRIEVE-SESSION-SCOPED-001`

## What & why

A **reprieve** is a governed, per-session, expiring, machine-checkable way to skip one or more PreToolUse guards for one agent session only. It replaces the current anti-pattern — commenting a guard out of the dispatcher's HANDLERS array (which disables it for *every* agent, forever, with no reason/approver/expiry, and turns the dispatcher into a drifted file `caws init` won't update).

**Model:** mirrors the danger-latch + scope-guard-strike substrate exactly (per-session JSON state file, keyed by sanitized session id, under the vendor state dir, gitignored, created/cleared by a dedicated reset-style command) — with one addition: an `expires_at` field, because a reprieve without expiry is the workaround with extra steps.

## The record

State file: `${CAWS_PROJECT_DIR}/${CAWS_VENDOR_DIR}/hooks/state/guard-reprieve-<sanitized-session>.json` (same dir as the danger latch).

```json
{
  "session_id": "019f6289-d6d6-76b3-a6d1-04123944b2e6",
  "created_at": "2026-07-15T07:00:00Z",
  "expires_at": "2026-07-16T00:00:00Z",
  "approved_by": "darianrosebrook",
  "reason": "agent editing casr-context.sh under CASR-HOOK-LIVE-WIRING-OWNER-STEP-01",
  "handlers": ["protected-paths.sh"]
}
```

- Keyed by sanitized session id in the filename (`sanitize_session` from `lib/caws-state.sh` — the shared transform the latch reset taught us to centralize).
- `handlers`: comma-separated list at create time → JSON array. **This is the "both" you asked for** — the dispatcher skips invocation for any handler in the list, and individual guards *may* consult the same record for finer-grained self-skip (though dispatcher-skip is the default and covers all guards uniformly).
- `expires_at`: ISO-8601. The reader treats an expired file as absent (derived, never mutated on read — same discipline as waiver `expires_at`).
- **No kernel/store/governance-state changes.** Like latch/strike files, this is operational cache under the vendor dir, gitignored — not `.caws/` authority state. It does NOT go through `events.jsonl` or the kernel.

## Enforcement seam (the dispatcher skip)

New shared lib: `templates/hook-packs/shared/lib/reprieve.sh`, sourced best-effort by `run-handlers.sh`. Exposes `caws_is_handler_reprieved <handler> [<session-id>]` → returns 0/1.

In `run-handlers.sh`'s loop, between handler-path resolution (line ~150) and invocation (line ~163) — the exact seam `post_tool_use.sh` already uses for `CAWS_DISABLED_HANDLERS`:

```bash
if declare -F caws_is_handler_reprieved >/dev/null 2>&1 && \
   caws_is_handler_reprieved "$handler" "$CAWS_RESOLVED_SESSION_ID"; then
  printf '[reprieve] %s skipped for session %s (expires %s)\n' \
    "$handler" "$_sid" "$_exp" >&2
  continue
fi
```

- `declare -F` guard → feature is a no-op when the lib is absent (fail-open, matching every other best-effort source in the hook pack).
- The skip is **logged to stderr** (`[reprieve] ...`) so the audit trail shows when/why a guard was skipped — the thing a silent guard self-skip or a commented-out HANDLERS line cannot provide.
- **Mirror in `codex/hooks/lib/run-handlers.sh`** (the vendored override) or that surface loses the feature.
- `run-handlers.sh` resolves the session id once at the top of `run_handlers` (source `lib/session-id.sh`, call `resolve_caws_session_id "$HOOK_SESSION_ID"`) so the check has the boundary-crossing identity, not just raw `HOOK_SESSION_ID`.

## The CLI surface — `caws reprieve`

New command group mirroring the reset scripts' flag vocabulary (`--current/--session/--all`, mandatory `--reason`):

```
caws reprieve grant [--current | --session <id>]
                    --handlers <comma-separated>   # e.g. protected-paths.sh
                    --reason "<why>"               # mandatory, recorded
                    --approved-by <who>            # mandatory
                    --expires-at <iso>             # mandatory (the one addition over the latch model)
caws reprieve show [--current | --session <id>]
caws reprieve revoke [--current | --session <id>] --reason "<why>"   # mandatory reason, like the latch reset
caws reprieve list
```

- `grant` writes the state file (atomic write via the shell-side temp+rename pattern the latch writer uses).
- `revoke` deletes it (`rm -f`, matching the latch reset) and appends an audit line to `${CAWS_VENDOR_DIR}/logs/guard-reprieves.log` (JSONL, matching `danger-latch-resets.log`).
- `show`/`list` are read-only.
- The session id for `--current` is resolved via `resolve_caws_session_id` (same as `reset-danger-latch.sh`), so it works from a human shell with no session env too.

This is a **new TS command group** (in `packages/caws-cli/src/shell/commands/reprieve.ts`), registered in `register.ts` + `command-metadata.ts`. It writes shell-side state files (not `.caws/` governance state), so it does NOT need a store writer or kernel type — it's a thin CLI over a JSON state file, like the reset scripts are thin shell over their sentinels.

## What this is NOT (scope boundaries)

- **Not path-scoped** this slice (your call: session-scoped only). Path globs are a documented follow-up; the record schema reserves nothing for it, keeping the first slice simple.
- **Not a waiver extension.** Waivers bypass GATES (policy-run time, `.caws/waivers/`, governance state, kernel-adjudicated). Reprieves skip HOOK guards (dispatch time, vendor state dir, operational cache, shell-adjudicated). Different enforcement layers, different substrates, different lifetimes — deliberately separate.
- **Not governance state.** Like latch/strike files, reprieve files are gitignored operational cache. They do not go through `events.jsonl`, the kernel, or `.caws/`. This keeps the change surface small and the lifecycle bounded.
- **No new kernel/store packages.** The whole feature is CLI + hook-pack; no `packages/caws-kernel` or `packages/caws-store` changes.

## Risk-tier

**Tier 2.** This touches the guard-skip path (a safety surface), but it is strictly *narrowing* a guard's reach for one session with mandatory reason/approver/expiry + audit log — it does not weaken the partition for other sessions, and the default (no reprieve file) is exactly today's behavior. The foreign-session partition holds by construction (filename is keyed to a different session id). Tier 1's tightest budget + always-request-review would be defensible too, but the change is additive and the blast radius is one gitignored state file per session.
